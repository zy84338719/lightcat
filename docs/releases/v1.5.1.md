# v1.5.1 —— 可靠性补丁：janitor panic 静默停摆、trace_id 日志洪水、webhook 重试与串联

v1.5.0 的收尾修复。**数据库有一条迁移**（`informs` 表加 `trace_id` 列），
升级即换二进制，无需改配置。

判定口径：**不引入任何破坏性契约**。API 的 JSON 形状、状态码、Cookie、
405/404 语义、零断点重启全部保持；新增的错误码与 trace 字段都是加的。

## 1. 周期循环一轮 panic 会静默停摆（cwmp / cmd）—— 本版最要紧的一条

三处周期循环（离线巡检 / 会话清理 / ontweb 采集）原先都是「整个 for-select 塞进
一个 \`goBg\` 任务」：

\`\`\`go
s.goBg(func() {
    t := time.NewTicker(interval)
    for {
        select {
        case <-ctx.Done(): return
        case <-t.C: doSomething()   // ← 这一轮 panic 会带走整个循环
        }
    }
})
\`\`\`

一轮 panic 虽然被 \`async.GoSafe\` recover 了、**进程不崩**，但那会同时带走循环协程：
离线巡检停摆 → 设备离线永远不会被判出来；会话清理停摆 → 超时会话永不释放，
\`byID\` 一直涨；ontweb 停摆 → 光功率趋势不再更新。

而且**没有任何告警** —— recover 把 panic 吃干净了，表现为「功能慢慢不工作了但
日志里什么都看不到」，是最难查的那类问题。

现在三处都交给 \`oekit/concurrency/loop\`，它把四个易漂移的语义一次钉死：单轮 panic
收编、停机排水、忙时丢 tick、首跑延迟可被打断。其中**停机排水**直接续上 v1.5.0
的关停契约（关库时正在写库的巡检不会被拦腰砍断）。

先写测试复现再改：手写版本第 3 轮 panic 后 120 ms 内只跑了 3 轮（\`---\nFAIL\`），
换成 loop.Run 后同场景通过。

## 2. trace_id 被客户端灌爆日志（web）—— 安全修复

新增 trace_id 时手搓的中间件有个漏洞：客户端传入的 \`X-Trace-Id\` 被**原样采信**，
逐字写进该请求的每一条日志行。实测一个带 2000 字节 \`X-Trace-Id\` 的请求：该值的
前缀出现在 **11 行**日志里，日志最长行 **2196 字节**。单个请求就能灌爆日志，
配上可换行的值还能伪造日志条目。

换成 \`oekit/middleware/hmw\` 的中间件后同一个请求：污染行 **0**，最长日志行
262 字节，落库的是合法 12 位十六进制。hmw 还多做了三处注入的一致性
（响应头 / RequestContext / 标准 ctx）与客户端 ID 的白名单校验。

## 3. 告警 webhook 改有界重试（alert）

原来失败只记日志、不重试。理由「重试风暴对家庭网络没好处」前半句对（所以不该无限
重试），但「完全不重试」对幂等接收端（Grafana / Alertmanager / 自建转发器）偏保守：
一次网络抖动导致的推送是白白丢的，而接收端根本不知道你来过。

四个上界缺一不可：次数 3、单次退避 8s、抖动 500ms、单条总时长 30s。只对可重试错误
重试（连接失败 / 超时 / 429 / 5xx）；其余 4xx 是接收端**明确拒收**，重试毫无意义。

关停契约上有个坑值得记：issue 里只提了「退避等待要能被 ctx 打断」，但 \`hc.Timeout\`
是 10s、比关停窗口（5s）还长，接收端根本不回时会卡在 \`hc.Do\` 里整整 10s，把库写入
排空的时间挤掉。所以请求本身也绑了进程 ctx，两种卡法都补了测试。

## 4. 设备上报 trace_id 串联（cwmp / web）

一次设备 Inform 会打出「收到 Inform」「已入队：取设备基本信息」「入队采集光功率」
等十几条日志，散在 cwmp / web 两层，用户报障贴一段日志出来，我们没法回答
「这十几条是不是同一次上报」。

现在一次 Inform 触发的全部日志共用一个 trace_id。**落库到 \`informs\` 表**（迁移 #18），
面板「上报记录」多一列、点一下复制 —— 用户报障时贴这一个值，我们就能在日志里捞出
整条链。

配套改法记一笔：trace_id 挂在 ctx 上，而 \`slog.Logger.Info\`（无 Context 变体）
**根本拿不到 ctx**，靠调用点加属性等于 111 个日志点都要记得传。所以做成
\`internal/trace.SlogHandler\` 包一层 \`slog.Handler\`。用户可见的日志格式不变，
末尾多一个 \`trace_id=\`。

## 5. 两条被实测否决的「优化」（store / web）

v1.5.0 的压测文档里挂着两条写入优化待办，这次按「先测再动」的原则验了，**两条都是
反向的**，已从文档改成实测结论，免得后人对着一份看起来很有道理的待办去优化一遍。

**批量多行 INSERT：慢 1.7 倍。** 一批 200 条参数：

| 写法 | ns/op | allocs/op |
|---|---|---|
| 逐行 Exec（现状） | 418,194 | 2813 |
| 多行单语句 chunk=50（最优点） | 717,827 | 1095 |

分配少一半却慢 1.7 倍，chunk 从 5 到 200 全扫过没有一档能赢，缓存 SQL 文本
（按行数缓存预编译语句）也救不回来（830 µs）。原因不是解析：逐行版本来就只
Prepare 一次，多行版把 200 行塞进一条反而让 SQLite 的 upsert 走不了逐行快路径。

**复用 prepared statement：只占 4.6%。** Prepare 单独量 20 µs，整批 418 µs。
且 \`MaxOpenConns(1)\` 下事务已占住唯一连接，要复用必须在 \`Begin\` 之前备好
（事务内再 \`db.Prepare\` 会死锁，实测踩过）。

另外 v1.5.0 关闭的 OEK-6（settings 缓存）基线也补测了：\`GetSetting\` 3.8 µs，
是面板本来就在做的那些查询里**最便宜**的，占 P95 预算 0.008%，不做。
