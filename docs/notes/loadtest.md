# 压测：大规模断电恢复（设备集体上电）

场景：机房/小区整体断电恢复后，所有设备几乎同一瞬间发 `1 BOOT` 冲向 ACS。
要回答的问题是「ACS 的并发上限在哪、瓶颈是什么」。

跑法（脚本都是现成的）：

```bash
scripts/loadtest.sh                       # 阶梯 10/50/100/200/400
scripts/loadtest.sh -n 200                # 只跑一档
scripts/loadtest.sh -N "50 150" -e 4484   # 自定义阶梯与每台参数规模
scripts/loadtest.sh -E "ACS_DB_MAX_CONNS=4"   # 透传 ACS 环境变量（调优对照用）
```

每档都用**全新的库和实例**（所有设备都是新设备 = 最坏情况），产物落在
`~/Desktop/TEMP/loadtest/<时间戳>/`：`summary.txt` + 每档的 `acs.log` / `sim.log`。

## 设备模板：照真机华为 V271-20

| 项 | 值 |
|---|---|
| 数据模型 | TR-098（`InternetGatewayDevice.`）|
| FTTR 子设备 | 3 台，光纤组网（带光功率参数）|
| `X_HW_APDevice` 子树 | **4484 个参数**（真机实测就是这个量级）|
| 每台参数总量 | ≈ 4700 个（ACS 纳管时会枚举 + 取值 + 全部落库）|
| 上报方式 | 单进程 `-count N` 模拟 N 台，全部同时发 `1 BOOT`，事件后退出 |

## 结论

1. **并发会话本身不是问题**：200 台设备同时建会话、同时领任务，小参数时 10.3 秒全部干净完成
   （200/200、0 错误）。ACS 没有并发上限、不拒绝新会话，也不需要排队。
2. **瓶颈是「每台设备的参数写入量」**：4 核机器上 ACS 全程只用 **1.05–1.14 个核**，
   吞吐卡在 **约 1.6–1.8 万参数行/秒**（≈ **3.5–4 台 V271 规模设备/秒**）。
   原因就是 `SetMaxOpenConns(1)`：一个连接把所有读写串行化，多核用不上。
3. **30 秒口径**（CPE 常见的 HTTP 超时）：**≤100 台可干净完成**（100 台 26s）；
   200 台约 60s、400 台约 2 分钟 —— 超时的设备**数据其实已经全量入库**
   （940,600 / 1,835,064 行 = 每台 4702），只是会话要在它下一次周期上报时收尾。
   现场表现就是「恢复供电后一两分钟内设备陆续都上来了」，不需要人工干预。
4. **不要靠调大连接池来提速**：1 → 4/8 连接虽然把 200 台从 59s 拉到 25s / 17.7s，
   但出现 195–196 条 `database is locked (SQLITE_BUSY)`，参数只入库 44% / 32%，任务领取也失败。
   `busy_timeout(5000)` 挡不住这种长事务冲突（一批就是几千行的 upsert）。
   **`SetMaxOpenConns(1)` 是正确性要求，不是保守做法** —— 所以这个口子没有做成配置项。
5. 想再往上提速，得改写入路径本身。**注意下面两条曾被列为待办，实测后已被否决**
   （2026-10-17 补测，数字见 `internal/store/params_bench_test.go`）：
   - ~~批量多行 `INSERT ... ON CONFLICT` 代替逐行 upsert~~ → **实测是反向优化，别做**。
     一批 200 条：现状逐行 Exec **418 µs / 2813 allocs**，多行单语句最优点（chunk=50）
     **718 µs / 1095 allocs** —— 少一半分配却慢 **1.7 倍**。chunk 从 5 到 200 全扫过，
     没有一档能赢。缓存 SQL 文本（按行数缓存预编译语句）也救不回来（830 µs）。
     原因不是解析：逐行版本来就只 Prepare 一次（SQL 只解析一次），多行版把 200 行
     塞进一条语句反而让 SQLite 的 upsert 走不了逐行的快路径。
   - ~~复用 prepared statement~~ → Prepare 单独量是 **20 µs**，一批总共 418 µs，
     只占 **4.6%**。而且 `MaxOpenConns(1)` 下事务已占住唯一连接，要复用就必须在
     `Begin` 之前备好（事务内再 `db.Prepare` 会死锁，实测踩过一次）。4.6% 不值那个复杂度。
   - 仍然值得做的是：
     - 「单写线程 + 队列批量提交」，让写库变成顺序大事务；
     - 少写点：`X_HW_APDevice` 下 4484 个参数是否都要落库（界面只用到其中一部分），
       或者对稳定子树改成「变化才写」。
6. 压力测试自身的两个坑（值得记，第一次踩到差点拿到假数据）：
   - 同一进程里模拟 N 台设备时，它们默认共用 `127.0.0.1` 和同一个 User-Agent，
     而 ACS 的会话兜底指纹是 `来源 IP + UA + 账号` → **N 台设备被当成同一个会话**，
     任务串到别的设备上、大部分直接被 204 结束。现在每台设备绑一个 `127.0.0.0/8` 里的独立源 IP
     （真机各有各的管理 IP，这才是真实形态）。
   - 真机（和规范）会回传 session cookie，模拟器原来没做 → 也补上了。
     两个都修完，压出来的数字才和现场对得上。

## 现场建议

- 一般规模（几十台到一百多台）**不需要任何调优**：断电恢复后设备会在各自周期内陆续上报完，
  人不用管。
- 几百台同时恢复时，关注的是「多久全部上来」而不是报错：实测 400 台约 2 分钟数据全量入库，
  只不过部分设备的单次会话会超时、留到下一次周期补完。想更快就得改写入路径（见上）。

## 面板静态资源：Hertz 原生路由 vs 兜底（issue #9）

`/static/`（style.css + app.js）是面板每次开页必取的热路径，以前整棵 `http.ServeMux`
经 `adaptor.HertzHandler` 挂在 Hertz 的 `/*any` 兜底上，每个请求都多走一跳
`net/http.Request ⇄ hertz.RequestContext` 转换。

### 先纠一个前提：`adaptor.StaticFSHandler` 并不绕开 adaptor

issue 里建议的一行是 `adaptor.StaticFSHandler("/static", assets)`。看 v0.5.2 的实现，
它最后一行是 `adaptor.HertzHandler(http.StripPrefix(...))` —— **转换照走**，
只是省掉了 mux 的路由匹配。另外它不带 `Cache-Control`，
会把「改完 app.js 刷新就用上」这条行为悄悄弄丢。

### 测法

服务器与压测客户端**分成两个进程**（否则客户端开销会混进 CPU）：

- 服务器 = `internal/web` 的 `go test -c` 二进制，起一台「`/*any` 兜底 + 静态路由」的同构引擎；
- 客户端 = 独立 Go 程序，闭环压 `GET /static/style.css`，32 并发；
- CPU 取服务器进程的累计 CPU 时间（`ps -o time=`），**每请求 CPU = 累计 CPU / 请求数**；
- 三种变体各跑 15–20 秒，并且**倒序再跑一轮**（baseline 先跑会吃到热缓存优势）。

### 结果（每请求服务端 CPU）

| 变体 | 第 1 轮（正序） | 第 2 轮（倒序） | 均值 |
|---|---|---|---|
| 现状：mux 兜底（adaptor + FileServer） | 41.58 µs | 43.61 µs | **42.60 µs** |
| `adaptor.StaticFSHandler`（issue 的写法） | 42.42 µs | 41.65 µs | **42.04 µs** |
| Hertz 原生 handler（本次采用） | 40.26 µs | 37.02 µs | **38.64 µs** |

`StaticFSHandler` 与现状**基本持平**（印证它没绕开 adaptor）；原生 handler 省约 **9%** 每请求 CPU。

### 为什么 QPS 数字不要看

QPS 在这三种变体间抖动比收益还大（同一次配置 baseline 就能跑出 70k–94k），
因为 35 KB 的响应体传输占了绝大部分时间，机器是**带宽饱和**而非 CPU 饱和。
真正干净、且与机制对得上的指标是**每请求服务端 CPU**：它只随服务端做的事变。
这也意味着端到端 p99 在真实面板流量（几个人访问）下基本看不出差别 ——
这个改动的价值是实打实的 CPU 节省，不是延迟。

### 行为差异（有意为之，都钉在 `static_test.go` 里）

- 404 不带 `Cache-Control`（与改前一致：`net/http` 的 `serveError` 会摘掉缓存头）；
- 不再发 `Accept-Ranges`（没有实现 Range，就不宣称；CSS/JS 本来也不会 Range 请求）；
- `GET /static/`（目录本身）改回 404，不再返回文件列表；
- 面板 mux 里**不再**留静态资源兜底 —— 否则「原生路由没注册」会被悄悄掩盖，
  `TestStaticReverse_FallsBackToCatchAll` 就失去意义。
